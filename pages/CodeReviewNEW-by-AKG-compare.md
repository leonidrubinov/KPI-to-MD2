| **Аспект** | **As-Is (текущая редакция)** | **To-Be (предлагаемая редакция)** |
|------------|-------------------------------|------------------------------------|
| **Суть документа** | Описание метрики (показателя CodeReview) и методики её расчёта. | Полноценная **практика работы** с чёткой целью, ролями и действиями. |
| **Цель** | Не сформулирована как цель практики; есть разделы «Для чего это компании» и «Для чего это команде». | Сформулирована единая цель: обеспечить контроль качества, соответствие стандартам, распространение знаний, снижение дефектов. |
| **Задействованные роли** | Упоминаются только исполнители (разработчик, архитектор) и контролёры, но без детализации действий. | Чётко выделены 4 роли: Разработчик, Прикладной архитектор, Руководитель команды, Тестировщик (опционально). Для каждой роли описан набор конкретных действий. |
| **Действия по ролям** | Отсутствуют; есть общие «Действия команды» без привязки к ролям. | Каждая роль имеет свой перечень обязанностей: разработчик создаёт MR и исправляет замечания, архитектор проводит ревью с содержательными комментариями, руководитель назначает дублёров и контролирует, тестировщик проверяет тестируемость. |
| **Критерии соблюдения практики** | Есть «признаки осознанности» (обязательные и дополнительные), но они смешаны с методикой расчёта процента. | Критерии выделены отдельно: обязательные (например, номер задачи в MR, содержательный комментарий, закрытые замечания) и дополнительные (участие других разработчиков, ссылка на ADR). Чётко определено, что для соблюдения практики нужны все обязательные и хотя бы один дополнительный признак. |
| **Расчёт показателя** | Подробно описан, но без чёткого разделения на задачи, подлежащие проверке, и целевые значения (мин/норм/макс) даны в процентах. | Сохранён аналогичный расчёт, но добавлено: целевые значения (норма 70%), и указано, что учитываются и дополнительные задачи (если ревью проведено). |
| **Действия при низком показателе** | Есть разделы «Действия команды, чтобы показатель был в норме» и «Действия команды для улучшения показателя» (после одного или двух спринтов). | Аналогично, но более структурировано: базовые действия для всех, действия после одного спринта, после двух и более. Добавлены рекомендации по использованию ИИ-ассистентов и автоматических проверок. |
| **Использование ИИ и автоматизации** | Не упоминается. | Добавлено: использование ИИ-ассистента для предварительного анализа кода, генерации тестов; интеграция статического анализатора (SonarQube) для снижения ручной нагрузки. |
| **План внедрения** | Отсутствует. | Предложен поэтапный план на 2 квартала: быстрый старт (обучение, назначение архитекторов, настройка дашборда), автоматизация и расширение, закрепление и непрерывное улучшение. |
| **Структура документа** | Разбита на пункты: описание, цель, методика расчёта, критерии, частые вопросы, действия команды. | Структура приведена к единому шаблону практики: введение, цель, задействованные роли, действия по ролям, измеримые критерии, действия для улучшения, итоговый список ролей с KPI, план внедрения. |
| **KPI для ролей** | Отсутствуют. | Для каждой роли предложены 1–3 ключевых показателя эффективности (например, для архитектора – процент выполненных ревью, среднее время проверки). |
| **Чёткость и однозначность** | Некоторые формулировки расплывчаты (например, «желательно наличие лайков»). | Все требования формализованы: «обязательно», «должен», «не менее». Убраны неоднозначные пожелания. |
