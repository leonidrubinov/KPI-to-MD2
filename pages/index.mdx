# Навык преобразования материалов метрики Code Review в спецификацию

## Название
Показатель CodeReview

## Описание
Показатель CodeReview отображает, что код, попавший в релиз, был проверен и согласован с архитектором. Код-ревью считается осознанным при выполнении всех обязательных признаков и минимум одного дополнительного. Данные визуализируются на производственном дашборде на втором уровне "Качества разработки". Показатель рассчитывается на основе коммитов, попавших в отчётный период (производственный квартал или спринт), и отражает процент задач команды, прошедших код-ревью.

## Для чего это компании
Показатель CodeReview позволяет оценить уровень контроля качества кода и соблюдения архитектурных стандартов. Это снижает количество дефектов, особенно критических, повышает стабильность релизов и уменьшает затраты на исправление ошибок на поздних этапах. Компания получает объективную метрику для управления качеством разработки и выявления команд с низким уровнем инспекций.

## Для чего это команде
- Повышение качества кода за счёт выявления ошибок до тестирования и продакшена.
- Распространение знаний о кодовой базе и архитектуре продукта внутри команды, снижение эффекта "bus factor".
- Обмен опытом и лучшими практиками, выработка единого стиля кода и подходов к решению задач.
- Снижение времени поставки функций и количества НСЕ за счёт раннего обнаружения проблем.

## Методика расчета

### Задачи, которые попадают в расчет
#### Обязательные
- Требования с нормативной трудоёмкостью 40ч или более.
- Требования хотя бы с одним нормативом 3-го уровня сложности.
- Клиентские НСЕ (несоответствия) 1 и 2 приоритета, кроме НСЕ в состояниях "Есть решение" и "Отказано".
- Задачи типов: "Требование в спринте" с указанными выше условиями; "Несоответствие" (внешние для команды) 1 или 2 приоритета.

#### Дополнительные
- Коммиты по задачам, которые не удовлетворяют обязательным условиям, но при этом код-ревью проведено – такие задачи попадают в отчёт и могут положительно влиять на оценку по CodeReview.
- Задачи, реализованные системным архитектором. Для них код-ревью не обязательно, но если ревью проведено другим разработчиком, это идёт в плюс к KPI.

### Формула
Процент задач, для которых выполнен признак код-ревью, рассчитывается как:
`100 * sum(isReview) / count(ClientOrderID)`, где:
- `isReview` = 1, если по задаче выполнены все обязательные и хотя бы один дополнительный признак осознанности.
- `ClientOrderID` – общее количество задач команды за период.

Балл KPI вычисляется как:
`1000 * sum(isReview) / count(ClientOrderID)`.

### Период расчета
- Для квартального показателя: производственный квартал.
- Для спринтового показателя: спринт компании (начинается со второй среды, заканчивается вторым вторником).

### Частота расчета
- ETL-процесс `qtsc_CodeReview` запускается ежедневно в 7:00 по мск.
- Расчёт отчёта по CodeReview на стороне микросервиса выполняется по расписанию в 17:00 мск.
- Данные обновляются ежедневно в течение спринта, фиксация показателя происходит на последний день спринта.

### Источники данных для расчета
- Git-репозитории (gitflex/gift): информация о merge request, его названии, авторе, ревьювере, комментариях, лайках/дизлайках.
- RMS: структура продукта, роли "Прикладной архитектор", команды, ответственные лица.
- Данные о коммитах и задачах из JIRA (номер задачи, уникальный идентификатор, трудоёмкость, нормативы, приоритеты НСЕ).
- База данных производственного дашборда (схема `qtscproductiondashboard`, таблицы `qprgrd_productiongrade` и `qprgrd_productiongradevalue`).

## Критерии приемки метрики
### Целевые показатели (мин, норм, макс)
- Минимум: 0%
- Норма: 70%
- Максимум: 100%

### Роли, которые выполняют метрику
#### Исполнитель
- Разработчик, создающий merge request и вносящий изменения.
- Системный архитектор (сотрудник с ролью "Прикладной архитектор"), выполняющий ревью и approving merge request.
- В исключительных случаях (если задачу делал архитектор) – другой разработчик может выступить ревьювером, и это засчитывается в плюс.

#### Контроль
- Мониторинг показателя осуществляется через производственный дашборд и отчёты ETL.
- Кураторы из СДЛ и руководители команд контролируют выполнение признаков осознанности.
- При отсутствии архитектора требуется назначить дублёра с ролью "Прикладной архитектор" (согласование с архитектором команды и ЦПЧС).

## Частые вопросы

1. *Если на требовании 40ч или 3 степень сложности сделал merge request не архитектор, а другой разработчик, то данное требование не будет соответствовать признакам осознанности. Это верно?*  
   *Ответ:* Мерж-реквест может создать кто угодно. Но если мерж-реквест акцептует не архитектор, то это не расценивается как осознанное код-ревью. Если же требование делал архитектор, он может отдать мерж-реквест на ревью кому-то другому, и если тот акцептует – задача идёт в плюс в KPI.

2. *Если на ошибке 1-2 приоритета сделал merge request не архитектор, а другой разработчик, то данное требование не будет соответствовать признакам осознанности. Это верно?*  
   *Ответ:* Если мерж-реквест акцептует не архитектор, то НСЕ не будет считаться осознанным код-ревью. Исключение – если НСЕ исправлял сам архитектор, тогда код-ревью не нужно, но если оно сделано, то идёт в плюс KPI.

3. *Если нет кода под требованием/ошибкой, то оно не будет соответствовать признакам осознанности и попадет в отчет, как неосознанное. Это так?*  
   *Ответ:* Для требований код-ревью делается только для задач с нормативами, подразумевающими наличие артефактов. Для НСЕ проверяется состояние задачи – задачи в состояниях «Отказано» и «Есть решение» отсекаются.

4. *FA-Reports только один архитектор. В случае его отсутствия (отпуск, больничный, отгул) ни один проведенный код-ревью не будет засчитан как осознанный?*  
   *Ответ:* Требуется найти дублёра, согласовать его с архитектором команды и ЦПЧС (Ольшанский А./Ольков С.) и дать ему в структуре продукта роль Прикладного архитектора.

## Действия команды, чтобы показатель был в норме и выше в соответствии с Целевыми показателями (регламент как выполняется метрика)

1. Убедиться, что на все обязательные задачи (трудоёмкость ≥40ч, норматив 3-го уровня, НСЕ 1-2 приоритета) создаётся merge request.
2. В названии merge request обязательно указывать номер задачи (уникальный идентификатор).
3. Автор merge request и ревьювер должны быть разными людьми. Ревьювер должен иметь роль "Прикладной архитектор" в структуре продукта в RMS.
4. После создания merge request архитектор проводит ревью, оставляя развёрнутые комментарии (не "Ок" и не "Правильно").
5. Желательно наличие лайков/дизлайков от архитектора или других разработчиков (не автора).
6. Заполнять Description merge request информативно: краткое описание изменений, ссылки на задачу, контекст.
7. Следовать Инструкции по проведению code review: проверять архитектурные решения, скрытые зависимости, безопасность (OWASP TOP-10, SQL-инъекции, конфиденциальные данные, безопасное соединение, права доступа, XXE, уязвимости библиотек).
8. Все комментарии ревьювера должны быть закрыты (исправлены) до принятия merge request.
9. MR должен быть небольшим, самодостаточным, содержать изменения в тестах и проверку покрытия.
10. При несогласии – обсуждение в комментариях, затем лично, затем с командой, при необходимости – вынос на комитет архитекторов.

## Действия команды для улучшения показателя

### Если показатель ниже нормы после одного спринта
1. Провести ретроспективу с командой, выявить причины низкого процента: отсутствие архитектора, недостаточное внимание к ревью, большие MR, нехватка времени.
2. Назначить ответственных за ревью на каждую обязательную задачу.
3. Провести обучение или мастер-класс по проведению code review и стандартам безопасности.
4. Организовать кросс-ревью между разработчиками для распределения нагрузки и повышения вовлечённости.
5. Убедиться, что роль "Прикладной архитектор" назначена для всех продуктов команды, при необходимости назначить дублёра.

### Если показатель ниже нормы после двух спринтов и более
1. Привлечь куратора из СДЛ и ЦПЧС для анализа системных проблем.
2. Пересмотреть процесс планирования, чтобы закладывать время на ревью в оценку задач.
3. Внедрить практику обязательного добавления 3 человек в ревьюеры на каждый MR для повышения информированности.
4. Автоматизировать проверки (SonarQube, OWASP) для снижения ручной нагрузки.
5. Рассмотреть возможность выделения отдельного архитектора или ротации ролей.
6. Провести индивидуальные встречи с разработчиками, у которых часто отклоняют MR, для повышения качества кода.
7. Скорректировать целевые показатели на квартал с учётом текущих возможностей команды, но с планом выхода на норму.

## Цель команде в спринт по улучшению показателя

- Мин: проведена ретроспектива прошлых итераций на предмет причин снижения % задач, прошедших Code Review, выработаны мероприятия для повышения % задач, прошедших Code Review + отправлено письмо куратору со списком выработанных мероприятий.
- Норм: 70% задач прошло Review, внедрены мероприятия для повышения % задач, прошедших Code Review.
- Макс: 100% задач прошло Review.
