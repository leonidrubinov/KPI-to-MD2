# CodeReview

## Название метрики

CodeReview (Показатель CodeReview)

## Описание

Показатель "CodeReview" отображает, что код, попавший в релиз, был проверен и согласован с архитектором. Показатель отображается на производственном дашборде на втором уровне "Качества разработки".

Текст подсказки к показателю: "Код попал в релиз через мерж-реквест, который подтвердил архитектор, под реквестом есть комментарии или лайки/дизлайки от архитектора."

## Для чего это компании

нет данных

## Для чего это команде

Сформировано на основе алгоритма расчета, описания и источников данных:

- Показатель дает команде прозрачную картину, какой процент ее задач прошел код-ревью: по каждой задаче видны обязательные признаки (наличие мерж-реквеста, ревью архитектором) и дополнительные (комментарии, лайки/дизлайки).
- Таблица "Детализация по Code Review" позволяет команде увидеть по каждой задаче, какой именно признак не выполнен (красный круг), и целенаправленно устранить причину.
- Ежедневное обновление данных в течение спринта (ETL-процесс qtsc_CodeReview) позволяет команде отслеживать показатель и успеть довести его до нормы (70%) до фиксации значения на последний день спринта.
- Выполнение признаков метрики означает, что код команды, попавший в релиз, проверен и согласован с архитектором — это подтверждает качество разработки команды на дашборде (уровень "Качества разработки").

## Методика расчета

### Задачи, которые попадают в расчет

Для формирования отчета отбираются коммиты, выполненные в текущем производственном квартале. Коммиты должны принадлежать задачам, которые удовлетворяют условиям отбора:

- Задачи с типом "Требование в спринте", у которых трудоемкость больше или равна 40 часов;
- Задачи с типом "Требование в спринте", у которых норматив 3-го уровня сложности;
- Задачи с типом "Несоответствие" (внешние для команды) 1 или 2 приоритета.

Если коммит выполнен под задачей, которая не удовлетворяет условиям отбора, и проведен CodeReview, тогда эти коммиты попадают в отчет и могут влиять положительно на оценку по CodeReview.

Задача попадет в отчет CodeReview, если дата пуша (pushdatetime) входит в отчетный период (производственный квартал).

#### Обязательные

Обязательные признаки CodeReview по задаче:

- **MergeRequest** — наличие мерж-реквеста по номеру задачи;
- **Ревью провел архитектор** — автор реквеста и ревьювер разные люди или на merge request-е есть approve архитектора.

#### Дополнительные

Необязательные признаки CodeReview по задаче:

- **Комментарий** — наличие развернутых комментариев под реквестом. Комментарии "Ок" и "Правильно" не учитываются;
- **Лайки/Дизлайки** — наличие лайков/дизлайков не от автора мерж-реквеста.

### Формула

Итоговый признак CodeReview по задаче формируется из оценки признаков на задаче:

- Если выполнены два обязательных признака и хотя бы один из необязательных, тогда признак CodeReview считается выполненным.
- Если коммит выполнен сотрудником с ролью "Прикладной архитектор", тогда признак CodeReview считается выполненным. Оценка других признаков не производится.

Показатель по команде (за спринт и за квартал) рассчитывается как процент задач, для которых выполнен признак код-ревью:

```
Процент = (задачи с признаком green (поле color для показателя по задаче) для команды / общее количество задач команды) * 100%
```

Балл по команде за квартал (valuescore):

```sql
select row_number() OVER(ORDER BY 100* sum(isReview) / count(ClientORderID) desc) AS num,
       RP as 'РП',
       ccrTL.Name as TeamLeaderName,
       max(t.Name) as 'Команда',
       sum(isReview) as 'Проинспектировано',
       count(ClientORderID) as 'ВсегоЗадач',
       100* sum(isReview) / count(ClientORderID) as 'PRC',
       1000* sum(isReview) / count(ClientORderID) as 'KPI',
       TeamID,
       0 as MinKriteriy,
       70 as NormKriteriy,
       100 as MaxKriteriy
from EPC_ReviewCodeDetail p with(nolock)
     join rms.rms.dbo.tBSDevTeam t (nolock) on t.bsdevteamid = p.TeamID
     left join rms.rms.dbo.tClient ccrTL (nolock) on ccrTL.ClientID = t.TeamLeaderID
where ActualDate = @date
  and (@TeamID = 0 or TeamID = @TeamID)
group by RP, ccrTL.Name, TeamID
```

Агрегация на уровнях дашборда:

- На уровне команды — значение команды;
- На уровне РП — среднее между показателями его команд;
- На уровне ПЦ — среднее между показателями команд этого ПЦ;
- На уровне компании — среднее значение между показателями ВСЕХ команд.

### Период расчета

- **Квартал** (prgrd_codereview_quart): производственный квартал. Сохраняется и фиксируется в первый день производственного квартала за предыдущий квартал. Начало периода — дата начала производственного квартала, конец — дата окончания производственного квартала.
- **Спринт** (prgrd_codereview_sprint): спринт компании. Начало — каждая вторая среда, начиная с 23.11.2022; конец — каждый второй вторник, начиная с 06.12.2022. Сохраняется и фиксируется в первый день спринта за предыдущий спринт. В текущем периоде данные каждый день обновляются.

### Частота расчета

- Расчет отчета по CodeReview на стороне микросервиса выполняется по расписанию в 17:00 мск. Обработчик события по коммиту сохраняет данные по коммитам.
- Загрузка данных в витрину дашборда выполняется ежедневно с помощью ETL-процесса qtsc_CodeReview в 7:00 мск.
- ETL-процесс выполняется каждый день по настроенному расписанию, что обеспечивает актуальность данных. Данные сохраняются каждый день.

### Источники данных для расчета

- Витрина данных: схема **qtscproductiondashboard**, таблицы **qprgrd_productiongrade**, **qprgrd_productiongradescale**, **qprgrd_productiongradevalue**;
- ETL-процесс **qtsc_CodeReview**. В рамках ETL-процесса загружаются показатели:
  - prgrd_codereview_quart — балл CodeReview по команде за квартал;
  - prgrd_codereview_sprint — балл CodeReview по команде за спринт;
  - prgrd_codereview_tsk — оценка CodeReview по задаче;
  - prgrd_codereview_Request — наличие на задаче реквеста;
  - prgrd_codereview_Comment — наличие комментария;
  - prgrd_codereview_Review — признак ревью;
  - prgrd_codereview_like — признак лайка;
- Данные по коммитам (обработчик события по коммиту), отчет EPC_ReviewCodeDetail;
- RMS: команды (rms.dbo.tBSDevTeam), сотрудники (rms.dbo.tClient), роль "Прикладной архитектор";
- Схема qtmteam: участники команды и роли (qmpart_eventparticipant, qmpart_eventparticipantrole), таблица qtm_team;
- mdpemploee: определение ФИО сотрудников;
- dqdp: определение проекта, продукта и клиента по уникальному номеру задачи;
- Трекер задач: идентификатор задачи определяется по уникальному номеру задачи (uniqueid).

## Критерии приемки метрики

### Целевые показатели (мин, норм, макс)

Согласно таблице qprgrd_productiongradescale (для prgrd_codereview_quart и prgrd_codereview_sprint):

| Критерий | Значение |
| --- | --- |
| Минимум (minscale) | 0 |
| Норма (normscale) | 70% |
| Максимум (maxscale) | 100% |

Линия нормы (зеленая) на графике установлена на уровне 70%. Линия компании (бордовая) показывает среднее значение показателя по компании.

### Роли, которые выполняют метрику

#### Исполнитель

- Разработчик (Developer) — автор коммитов/мерж-реквестов;
- Ревьюер (Reviewer) — ревью проводит сотрудник, определенный в качестве Прикладного архитектора для PBC. Прикладной архитектор определяется в RMS.

Ответственная команда определяется по команде, выбранной на задаче.

#### Контроль

Владелец производственного показателя — Оржевская Н.

По каждому значению показателя определяются: РК (Руководитель команды), РП (Руководитель продукта), Agile-коуч (куратор), ПЦ — по команде (TeamID) в схеме qtmteam.

## Пример расчета (с подставлением данных в формулу)

Пример составлен на основе методики расчета, описанной в концепции.

**Шаг 1. Оценка признака CodeReview по задачам команды.**

Допустим, у команды в спринте 5 задач, попадающих в расчет:

| Задача | MergeRequest (обяз.) | Ревью провел архитектор (обяз.) | Комментарий (доп.) | Лайки/Дизлайки (доп.) | Признак CodeReview (color) |
| --- | --- | --- | --- | --- | --- |
| Задача 1 | 1 | 1 | 1 | 0 | выполнен (green) |
| Задача 2 | 1 | 1 | 0 | 1 | выполнен (green) |
| Задача 3 | 1 | 1 | 0 | 0 | не выполнен (red) — нет ни одного дополнительного признака |
| Задача 4 | 1 | 0 | 1 | 1 | не выполнен (red) — не выполнен обязательный признак |
| Задача 5 | коммит выполнен сотрудником с ролью "Прикладной архитектор" | | | | выполнен (green) — оценка других признаков не производится |

**Шаг 2. Подстановка данных в формулу.**

Формула:

```
Процент = (задачи с признаком green для команды / общее количество задач команды) * 100%
```

Подставляем данные из шага 1: задач с признаком green — 3 (Задачи 1, 2, 5), всего задач команды — 5:

```
Процент = (3 / 5) * 100% = 60%
```

**Шаг 3. Сравнение с целевыми показателями.**

60% < 70% (норма) — показатель команды ниже нормы.

## Частые вопросы

- **Не указан разработчик в детализации** — проблема может быть в следующем: по почте, указанной в git, не удалось определить сотрудника.
- **Не указан ревьюер в детализации** — если общий признак зеленый, а все остальные серые, тогда коммит сделал прикладной архитектор; либо по почте, указанной в git, не удалось определить сотрудника.
- **Что если на задаче сменилась команда?** Если на задаче выполнена смена команды или для продукта определен прикладной архитектор, тогда CodeReview будет пересчитан в момент расчета.
- **Как назначить роль "Прикладной архитектор"?** В RMS: Справочники → Структура продукта → Выбрать продукт → вкладка "Ответственные лица" → в контекстном меню выбрать "Добавить" → на форме "Ответственное лицо" нажать "Выбор сотрудника старым методом" → выбрать роль в поле "Роль" (нажать "Показать неактуальные роли", выбрать роль "Прикладной архитектор") → в поле "Сотрудник" выбрать сотрудника.

## Действия команды, чтобы показатель был в норме и выше в соответствии с Целевыми показателями (регламент как выполняется метрика)

На основе представленных данных (условия выполнения признака CodeReview):

- Создавать мерж-реквест по номеру задачи (обязательный признак MergeRequest);
- Обеспечивать проведение ревью архитектором: автор реквеста и ревьювер — разные люди, либо на merge request-е есть approve архитектора (обязательный признак);
- Оставлять развернутые комментарии под реквестом (комментарии "Ок" и "Правильно" не учитываются) и/или лайки/дизлайки не от автора мерж-реквеста (хотя бы один дополнительный признак).
